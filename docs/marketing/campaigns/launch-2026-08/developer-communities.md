## 正文

模型能力越来越强，但在真实研发项目里，“回答正确”通常只完成了很小一部分工作。

一个跨端 Bug 可能涉及 React 状态、Spring Boot 接口、SSE 或 WebSocket、数据库记录和容器运行时；一个 Issue 除了标题，还有评论、图片、附件、分支和验收状态；一次数据分析也需要先核对 Schema、指标口径和异常数据，再形成可复查 SQL 与看板。

如果 Agent 只有聊天上下文，人仍然要负责四件事：反复搬运事实、在多个系统间执行操作、保存中间产物、把结果写回原流程。要让 Agent 真正进入项目，工程上至少要补齐以下能力。

## 1. 项目级上下文，而不是一次性提示词

Agent 需要稳定的项目目录、会话和文件边界。会话必须绑定具体项目，文件和终端操作也应落在同一范围内。这样才能保证不同项目互不串扰，并让后续任务继续使用已有代码、文档和验证结果。

上下文持久化也不能只保存最终文本。任务过程、工具结果、生成文件和交付物需要被识别和展示，否则用户仍然难以判断 Agent 实际做了什么。

## 2. 面向真实系统的连接能力

工程团队的事实分布在 GitHub、GitLab、Gerrit、SVN、Jenkins、Docker、Kubernetes、SonarQube、Grafana、MySQL 和 Issue 系统中。Agent 需要通过受控工具访问这些系统，而不是要求用户把所有内容复制到对话里。

连接能力应区分只读和写入。数据库探查、日志读取和指标查询可以优先只读；变更生产资源、写入数据或更新业务状态时，需要明确授权和确认。

## 3. 可下载、可复查、可继续编辑的交付物

工程任务的结果往往不是一段回答，而是代码修改、脚本、SQL、Dashboard、PPTX、PDF、MP4 或验证记录。平台需要把这些文件和系统结果作为正式交付物，而不是从工具调用记录中临时猜测“可能生成过什么”。

交付物还应保留与项目、会话和任务的关系，方便团队下载、复核和继续迭代。

## 4. 团队共享与权限控制

企业环境中的 Agent 是团队资源。成员需要在统一权限和数量限制内创建 Agent、共享项目现场，并根据角色使用不同能力。模型连接和运行时配置可以集中维护，日常使用者不应被迫重复录入敏感配置。

对于数据库、Issue、终端和生产系统，还要进一步限制 Agent 能访问的具体项目、Schema、目录和动作。

## 5. 运行时与治理边界

Agent 运行时既可以在平台管理的容器中运行，也可以部署在目标机器上，通过受控链路连接平台。无论采用哪种方式，都需要处理会话恢复、实时消息、任务状态、文件同步、升级和异常恢复。

更重要的是，平台不能把“自动化”理解为“取消确认”。生产变更、数据写入、对外发布和重要业务决策仍然应按风险进入人工复核。

## Agents Platform 的实现方向

Agents Platform 将每个 Agent 作为一份持续存在的工作现场，包含项目、会话、文件、任务和交付物。当前提供七类内置 Agent：通用、数据库、网站开发、Issue 处理、Grafana、PPT 和视频。

典型工作包括：

- 从页面截图出发，沿前端、接口、实时消息和运行时定位并修复故障；
- 接管 Issue，读取评论与附件，完成修改、验证、回写和人工验收；
- 探查 MySQL 结构，把经营问题转成可复查 SQL 和 Grafana Dashboard；
- 把需求和材料交付成网站、可编辑 PPT 或带旁白视频。

平台由客户部署在自己的 Linux 环境中，项目和业务数据由部署方管理。当前正式版本为 v1.0.5，支持 Linux x64 全新安装和从 v0.0.1 及后续正式版本累计升级。

官方未修改的二进制安装包仅供自然人个人非商业使用。Agents Platform 是专有软件，不是开源软件；公司、组织或商业用途需书面授权。
